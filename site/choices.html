Why this matters

Where we found it: cross-checking Roboflow’s polygon and mask exports against masks loaded by Supervision exposed different pixels for the same annotation.

Who encounters it: for example, Roboflow’s RF-DETR uses pycocotools for COCO masks, so a Supervision-based check can disagree before any model prediction. Boundary differences can change area, IoU, training targets, and mask AP, especially for small or thin objects.

Benchmark comparisons: reproducing published results requires matching mask conversion too. Any effect on a specific paper or hosted Roboflow score still needs its evaluation pipeline to be checked.

What an export fix must include

Choose encoding independently of iscrowd: RLE must not turn an instance into a crowd. Test pixels, thin regions, holes, multiple parts, and metadata through export and both readers.

What remains a trade-off

New RLE exports cannot repair old polygon files. Switching their importer can still change masks. Polygon-only consumers need the explicit lossy export—or a separately tested boundary-tracing solution.

Why switching gains some alignment, but not universal compatibility

COCO paths in RF-DETR, Detectron2, and torchvision’s reference loader use pycocotools. Ultralytics’ helper truncates vertices before OpenCV fill; Supervision’s COCO loader rounds. These are operation-specific alignments.

Scope, sources, reproduce

Only COCO import/export is considered here. Generic drawing and other formats keep their behavior. Reference import needs pycocotools (potentially a COCO extra); missing dependencies should error, not silently select a different fill.

Export evidence: Supervision’s COCO exporter. With no explicit crowd flag, it already selects RLE for some topologies; the examples keep iscrowd=0. Recent #2587 changed rounding, not the older inclusive fill.
