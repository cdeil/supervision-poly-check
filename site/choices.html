Three steady-state choices

Scope: COCO polygon loading

  1. 1 Keep the current behavior

    One result: existing Supervision masks.

    Gain
    Keeps current masks and other loaders’ rounding/fill convention. No new mode or dependency.
    Cost
    COCO polygons still differ from the reference. Users needing parity must convert outside Supervision.
    Long term
    Document this as an intentional compatibility contract and test it.

  2. 2 Switch the COCO loader

    One result: COCO reference masks.

    Gain
    Aligns this loader with pycocotools and the COCO paths in RF-DETR, Detectron2, and torchvision.
    Cost
    Can change existing masks and contour-export round trips; diverges from other loaders’ fill rules.
    Long term
    One format-specific contract; choose a release boundary, dependency policy, and export follow-up.

  3. 3 Offer both explicitly

    Two named modes; default chosen separately.

    Gain
    Reference parity and legacy reproducibility are both available inside Supervision.
    Cost
    Callers must understand the choice. Two behaviors need ongoing tests, documentation, and support.
    Long term
    A permanent API commitment. PR #2714 currently keeps the legacy default.

No warning/deprecation phase is proposed here. Option 2 can be a documented direct change; option 3 need not imply a later default switch.

So, yes: switching gains reference-loader alignment and loses exact compatibility with affected legacy Supervision results. It does not move the whole library from one universally consistent ecosystem to another.

A migration cost: old polygon exports

A 4 × 4 bitmap becomes a contour with vertices from (2, 2) to (5, 5) via sv.mask_to_polygons. Treating those stored numbers as COCO boundary coordinates changes the reloaded mask.

This rectangle round-trips today; arbitrary masks need not. Contour extraction and polygon simplification can already discard details. Changing the COCO loader does not itself repair export.

Export choices and limits

RLE can preserve a binary mask exactly, but export policy, consumer support, and iscrowd semantics still need review. A half-pixel translation alone does not turn a contour through pixel centres into an exact pixel-edge boundary. Single-pixel regions, thin structures, and holes need explicit tests.

Is it a bug, a convention, or a shift?

A COCO compatibility defect is fair when reference-equivalent COCO loading is the expectation. OpenCV’s drawing rule is not inherently a bug. The mismatch combines vertex quantization, coordinate interpretation, and edge inclusion; it is not a universal subpixel translation. Even at zero offset, the square has 25 versus 16 pixels.

Small or thin objects can be affected proportionally more. A dataset’s metric impact must be measured; these examples do not establish it.

Recent change ≠ new mismatch

#2587 changed COCO float handling from truncation to rounding and aligned it with other Supervision loaders. Inclusive OpenCV filling already existed in 0.20.0.

Recent work makes this a reasonable time to revisit the contract. It does not tell us how many downstream users depend on the older behavior.

What the cited paper does—and doesn’t—show

Parmar et al., arXiv:2104.11222 studies resizing, aliasing, and image compression in GAN evaluation. It shows that preprocessing details can materially affect comparisons. It does not select a polygon rasterizer for Supervision or establish fixed library camps.

The maintainer’s “Where are Pixels?” also separates coordinate grids from filtering. Matching coordinate origins alone does not guarantee matching masks.

Why users encounter this

Checking polygon exports against bitmap masks, or comparing ground truth across training and evaluation tools, can expose different pixels for the same annotation. Without an explicit contract, users have to diagnose that difference themselves.

For the maintainers: which contract should COCO import promise, which existing results must remain reproducible, and how should exported data behave?

Implementation scope, dependencies, and reproducibility
  • COCO-only: a polygon-loader change need not alter RLE decoding, box-only annotations, generic drawing, or other dataset formats.
  • One behavior does not require a global dependency: pycocotools could be required only for the relevant COCO feature. Missing dependencies should produce a clear error, not silently select a different rasterizer.
  • Reference fidelity has a maintenance cost: depending on pycocotools brings packaging/platform considerations. A separate reimplementation would need sustained parity tests; the examples here are not sufficient proof of full equivalence.
  • Evidence is versioned: this page measures Supervision 0.30.9, pycocotools 2.0.11, OpenCV 5.0.0.93, and NumPy 2.5.3. Source links pin the other inspected code paths. The contour example is illustrative, not a test of every export format or release.
